2. 日常操作：採集 → 整理 → 歸檔

A. 現場採集（不用中斷手上的事）

首頁四顆大按鈕，按了就開始：

  • 🎥 錄影／📷 拍照／🎙 錄音／✏️ 記事
  • 錄音每 10 分鐘自動分段上傳，斷網會先存在手機、有訊號再補傳
  • 錄音中拍的照片會自動標記「錄音第幾分幾秒拍的」，事後對得回逐字稿
  • 採集畫面上的資料夾 chip（錄音是浮動列上的 📂）可以當場歸類； 真的很急就按「⏳ 很急，先放暫存區」，一鍵帶過
  • 沒歸類的一律落在⏳ 暫存區——它是一個真的資料夾，永遠看得到， 不像舊版收件匣空了就從首頁消失
現場專心看展、做實驗就好。先採集，事後整理——這是這個 App 唯一的設計原則。

B. 一鍵整理（把聲音和圖變成文字）

有空時打開那筆紀錄，按 🪄 Cloudflare AI 整理：

  • 會把「還沒轉文字的錄音」全部轉、「還沒擷取文字的照片」全部擷取
  • 已經處理過的不會重跑，不浪費額度
  • 按鈕旁顯示「⏳ N 筆待整理」；顯示「✓ 已全部整理」而且反灰時，代表沒事可做，不用按
  • docx／xlsx／pptx／txt／csv 這類檔案不經過 AI，後端直接解出文字，不扣額度

C. 歸檔（隨時都能改，四層都搬得動）

  • 記事詳情的「位置」那一列按 📂 移動…：選擇器列出完整四層樹狀結構、 每一列標出第幾層，已經歸過檔的一樣能再搬（也能搬回收件匣）
  • 單一檔案：資料夾裡按 ⋯ → 📂 移動， 可以搬到任何一層，不再只能拖進「目前資料夾底下的子資料夾」
  • 整個資料夾也能搬：資料夾卡片的 ⋯ →「移動到其他資料夾」， 底下的子資料夾與記事一起走（超過四層時會擋下並說明原因）

C-2. 暫存區與 AI 自動歸類

  • 放進暫存區的東西，超過設定天數沒人動，排程就會用 AI 從 你現有的資料夾裡挑一個歸進去
  • 天數自己調，不是寫死的規則：首頁「待處理」下方那一行有輸入框， 直接改數字按「套用」，0～30 天都可以，改了立刻生效，不用重新部署。 沒調過的話預設 4 天
  • 填 0＝不等待，全部立即歸檔：暫存區裡不管放了多久（包括剛剛才丟進去的） 下次排程一到、或按「現在就跑一次」，全部馬上交給 AI 分類
  • AI 歸的位置會標上 🤖 AI 分類：點一下可以「確認正確」（拿掉標記）或自己改位置
  • AI 判斷不出來的不會亂塞，留在暫存區並標成「🤖 待人工」
  • 首頁「待處理」上方那一行會顯示暫存區還有幾筆、幾天後自動歸類，也可以按「現在就跑一次」；這個清單只列還沒真正歸檔的東西（收件匣、暫存區、AI 剛歸類還沒確認的），已經歸檔好的不會佔位置

C-2b. 判斷準則會自己長，但一定要你點頭才會生效

未來資料種類一定會變，判斷規則不該永遠寫死。系統會偷偷觀察一件事： 你把 AI 分錯的記事手動搬去某個資料夾好幾次，就代表那個資料夾 可能值得設一條關鍵字規則，以後同類內容不用每次都靠 AI 猜。

  • 累積到門檻次數（目前是 2 次），首頁「待處理」下面會出現一塊 🤖 分類規則建議的通知，寫著「最近有 N 筆記事被你搬進這個資料夾，例如……」
  • 規則不會自己生效：關鍵字一定是你自己填、按「採用」才會真的拿去用； 按「忽略」就當沒看到，下次同樣情況再發生還是會再問一次
  • 規則生效後，符合關鍵字的記事之後會直接歸檔，連 AI 都不用呼叫 （更快、更省 AI 額度），理由會標成「符合已知規則」，一樣是可以打開的 🤖 標記，不是黑箱
  • 規則之間打架（同時符合兩個資料夾）時系統不會硬猜，退回給 AI 判斷

C-3. 資料夾排序：每一層都能切時間／名稱

  • 資料夾工具列的 🔤 名稱排序 / 🆕 新到舊 按鈕：一按就切換， 首頁根層與每一層子資料夾同時套用，不用每層各切一次
  • 跟「＋ 上傳檔案」旁邊的 🆕 新到舊 / 🔤 檔名排序 是兩件不同的事：那顆管的是資料夾裡的檔案清單，這顆管的是資料夾本身的排列順序

D. 匯出給 AI 寫報告

資料夾右上角 📄 匯出給 AI → 產出一份 Markdown 原料包 （含所有逐字稿、擷取文字、欄位）→ 貼給 Claude 說「彙整成報告」→ 存進 Notion。

Notion 自動同步還沒做完（欄位有了但沒接通），目前這一步是人工貼上。

E-0. 內文編輯：Markdown 直接貼、蠟筆畫重點

  • 從 AI 回覆或 .md 檔複製一段 Markdown 直接貼進內文，標題、清單、程式碼區塊、 引言、分隔線會自動變成真的格式，存檔後也維持不變
  • 工具列的 🖍 是蠟筆（螢光筆）： 黃／綠／藍／粉／橘五色，用來畫重點

E. 記一句

紀錄詳情裡可以一句一句往下加，每句獨立寫入、不會互相蓋掉，適合邊聽邊記重點。

3. 檔案與文字擷取

上傳

資料夾工具列 ＋ 上傳檔案 可一次選多個檔， 每個檔自成一筆紀錄（標題＝去掉副檔名的檔名）。同一個資料夾裡內容完全相同的檔案會自動去重。

🔬 深度處理（圖形型 PDF 專用）

有些 PDF 是圖檔排版、沒有文字層（例如廠商用 Illustrator 做的型錄）， 一般整理抽不到本文。這時用深度處理：瀏覽器把 PDF 逐頁轉成圖片，再走照片 OCR。

這個只能手動一份一份指定，刻意不做背景批次——很吃 AI 額度。

🏷 整理檔名

把標準文件的檔名統一成 組織_編號_年份_中文標題（例 ISO_10555-8_2024_體外血液處理用導管.pdf），並移除內容完全相同的重複檔。 不會呼叫 AI，用既有的 OCR 與檔名資訊推。年份推不出來時不會硬猜， 會保持原檔名不動。

醫材分類

單一檔案可以掛醫材分類（CVC／HD／Pigtail／高壓注射筒組…），選項來自分類字典。 打錯字不會產生幽靈分類——存檔時會驗證。

🔗 關聯

兩筆記事之間可以建立關聯，例如「這次實驗引用了這份 ISO 標準」「這家廠商對照這篇專利」。 關聯是雙向的，而且必須手動建立過才查得到——系統不會自己猜。

🔍 這筆資料的來歷

每一筆記事詳情往下滑到底，有一段「這筆資料的來歷」，回答四個問題：

  • 這筆哪來的：現場採集／外部知識庫同步（含來源代號）／從 Medtec 匯入／ 透過 claude.ai 新增。如果原始資料已經從來源移除，這裡會警示
  • 誰在何時改過：完整的操作履歷，只增不刪
  • AI 動過哪些地方：每個附件的轉文字／擷取文字／深度解析狀態。 「已判定不需處理」代表跑過但沒有可擷取的內容（例如照片裡就是沒有字）， 不是漏掉——所以不會被重複扣費
  • 原始資料列（可展開）：Cloudflare D1 實際存的欄位長什麼樣。 超長的文字只顯示開頭並標明總長度
專利與法規場景需要的是「誰在何時記錄了什麼、依據什麼」的可稽核紀錄。 這一段就是為此存在——資料的來歷本身也是資料。

4. 資料夾架構與分類

四層架構

層級放什麼例子
第 1 層產品／專案中央靜脈導管（CVC）、血液透析導管（HD）
第 2 層文件類型法規與標準、驗證與確效、風險管理
第 3 層主題／試驗標準系列、試驗項目、國家／市場
第 4 層年份／版本年份／版本、單一標準文件、送件版本

最多四層，想建第五層會被擋下來。

⚙️ 管理分類

首頁「已歸檔資料夾」旁邊。分類存在資料庫裡，在這裡改完立刻生效， 不用改程式、不用重新部署。

  • 改名：既有資料夾上的分類文字會一起更新（同一個分類換叫法）
  • 刪除：只拿掉選項，既有資料上的分類文字保留不動，並告訴你還有幾筆在用

5. 外部知識庫自動同步

隨身記可以每天自動去外部的公開 JSON 抓資料進來（目前設定了 litdb 的三個收藏）。 台灣時間每天凌晨 02:00 自動跑，你不用做任何事。

它是怎麼運作的

  • 內容沒變就完全不動（比對內容指紋），只有真的改過的才更新
  • 你自己加的註記永遠不會被蓋掉：同步只改寫記事裡被 <!-- sync:start --> 與 <!-- sync:end --> 框住的那一段，你在這之後寫的東西不會被動到
  • 來源端刪掉的資料不會跟著刪，只會標記起來，要不要刪由你決定
  • 來源的專利分析內容（配方、FTO 風險、迴避設計）會存進「AI 深度解析」欄位， 搜尋查得到，而且看的時候會明確標示那是 AI 產出、不是你現場記的

要加一個新的知識庫

不用改程式碼，往來源清單加一列就好。三個關鍵欄位：

欄位意思
url公開 JSON 的網址
items_path資料陣列在 JSON 裡叫什麼（papers／reports／items…）
id_field每筆資料的唯一鍵欄位名（id／code…）
curl -X POST "https://fieldlog.gogoyankee.workers.dev/api/sources" \
  -H "x-pin: 你的FIELD_PIN" -H "content-type: application/json" \
  -d '{"key":"market","label":"市場分析",
       "url":"https://.../reports.json",
       "items_path":"reports","id_field":"code",
       "folder_parent":"LitDB 文獻庫"}'

想立刻同步、不等半夜

curl -X POST "https://fieldlog.gogoyankee.workers.dev/api/admin/sync-sources" \
  -H "x-pin: 你的FIELD_PIN"

一次跑完全部來源，不用自己翻頁。加 ?source=coating 可以只跑其中一個。

想知道「資料是不是過時了」，直接在 claude.ai 對話裡問，它會用 sync_status 工具告訴你每個來源最後同步的時間和筆數——不用靠記憶。

6. 用 claude.ai 問問題（MCP）

在 claude.ai 設定好 MyWiki 連接器之後，直接用講話的方式問就好， 它會自己決定要查哪裡。例如：

  • 「幫我查展商裡做親水塗層的」
  • 「上次實驗紀錄裡提到的固化溫度是多少」
  • 「litdb 裡有沒有講活檢針擊發機構的文獻」
  • 「wiki 的抗結痂條目現在寫到哪」
  • 「把 7/29 那筆 POM 膠測試的照片給我看」

四個讓查詢變準的技巧

① 查不到 ≠ 沒有這筆資料

最常見的失敗不是資料不存在，是關鍵字沒猜對。 叫它「先列出那個資料夾底下有什麼」，看檔名通常就知道要不要細看， 比反覆猜關鍵字有效得多。

② 內部代號查不到就當場補

公司內部代號、料號、慣用語（例如「BaClear」對應「抗結痂披膜」）只有你知道。 查不到的時候直接說「把 BaClear 加到抗結痂披膜的同義詞」， 它會用 add_synonym 補進去，下一次查詢立刻生效，不用改程式。

③ 照片可以直接叫它看，不是只能讀擷取出來的文字

斷面、外觀不良、現場擺設這種文字描述不出來的東西，直接說 「把那筆的照片給我看」，它會用 get_fieldlog_image 把照片本身取回來看。 只讀擷取文字（ocr_text）會漏掉重點——照片上沒有字的時候，擷取文字本來就是空的。

④ 看到「AI 深度解析」要留意

標示「AI 深度解析」的段落是 AI 整理／推論出來的，不是你現場記的原始證據。 要拿去寫報告或做決策前，回頭看原始內容或來源連結確認一次。

MCP 能改資料嗎？

只能新增，不能修改或刪除。22 個工具裡只有四支會寫入：新增一筆記事、 上傳一份附件、建立一個關聯、補一組同義詞。程式碼裡沒有任何一行能改掉或刪掉既有資料—— 就算你在對話裡叫它刪，它也做不到。要改內容、刪東西，一律回這個 App 自己操作。

架構：三個系統＋一層問答窗口，怎麼接起來的

medapi-mcp 本身不存任何資料，它只是一層轉接： 

claude.ai / Claude Code / ChatGPT
        │  自然語言問答（連接器網址帶 ?pin=MCP_PIN）
        ▼
   medapi-mcp（唯讀問答層，22 個工具）
        │
        ├── Service Binding → fieldlog /wiki/*（帶 FIELD_PIN）  … 策略地圖 Wiki 條目
        ├── D1 共綁 → fieldlog DB（幾乎全 SELECT，4 支工具 INSERT）
        │      … 隨身記紀錄／逐字稿／擷取文字／關聯／LitDB／同義詞表
        ├── D1 共綁 → medtec-2026 DB（SELECT）  … 拜訪狀態／共筆紀錄／附件清單
        └── Service Binding → medtec /data/exhibitors.json  … 展商主檔（公開靜態資產）

「Service Binding」是 Cloudflare 官方的 Worker 對 Worker 呼叫方式，直接呼叫對方程式碼、 不經對外網路（一般 fetch() 打同帳號下另一個 Worker 的網址會直接被擋掉，拿到 404）。 「D1 共綁」是同一顆資料庫同時掛在兩個 Worker 上——medapi-mcp 不用經過任何人， 直接下 SELECT 查 fieldlog／medtec-2026 的資料庫。

三把鑰匙，各自獨立，千萬別設成同一組： FIELD_PIN（隨身記自己的登入）、MCP_PIN（MyWiki 連接器登入）、 TEAM_PIN（參展系統自己的登入）是三個完全獨立的 Secret。 共用同一組密碼的話，換一次密碼就會連鎖搞壞好幾個系統——這是實際發生過的事故， 不是假設性的提醒。medapi-mcp 這個 Worker 比較特別，身上同時掛了 兩組 Secret：自己的 MCP_PIN，加上跟 fieldlog 完全同值的 FIELD_PIN（讀 Wiki 用），這兩個不要搞混。

7. AI 額度與成本

  • 轉文字／OCR 用 Cloudflare Workers AI，每天約 10,000 Neurons 免費額度， 隨身記與參展系統共用同一份
  • 自動處理只會用到 70% 安全額度（7,000），留餘裕給你手動觸發
  • 月付費有軟上限 USD 4.5，達到就停，不會靜默扣費
  • 首頁「Cloudflare 用量」區塊可以看目前狀況
用量數字是 Cloudflare 那邊回報的，可能落後一到數天。 看到「今日」數字沒動不代表沒在跑。

8. 疑難排解

畫面好像是舊版的

首頁標題旁邊有版本號（例 v57）。如果伺服器上是更新的版本， 畫面會直接跳出橘色警告並提供「一鍵清除快取」——按它就會解除 service worker、清掉所有快取、重新載入。

沒跳警告就代表你載到的確實是最新版，問題在別的地方。

查詢說「查無資料」但你確定有

  1. 先確認關鍵字沒打錯字
  2. 拿掉資料夾範圍限制，改成全庫查
  3. 叫 AI 先「列出資料夾底下有什麼」，用看的比用猜的準
  4. 確定只是用詞沒對上 → 用 add_synonym 補一組

系統查不到的時候會誠實告訴你它試過哪些詞，不會只回一句「查無」—— 就是要讓你分得出「真的沒有」和「有但沒對上」。

連 MCP 失敗／工具叫不出來

照下面順序排查，2026-08-05 這次真實發生過的完整案例就是照這個順序才挖到根因的：

  1. 401 錯誤、或連接器一直顯示「未連線」：確認連接器網址結尾是完整的 ?pin=...，值要跟 Worker 上目前的 MCP_PIN 一致。
  2. claude.ai 跳出「Couldn't register with sign-in service」，要你填 OAuth Client ID： 這通常不是真的要設定 OAuth——medapi-mcp 完全沒有實作 OAuth， 這其實是 claude.ai 把「呼叫失敗（多半是 PIN 不對）」誤判成「這台伺服器要走 OAuth 註冊流程」 才跳出的誤導性錯誤訊息。先照上一步確認 PIN，不用真的去找 OAuth Client ID。
  3. Dashboard 上明明有設定 Secret，卻還是回「尚未設定 MCP_PIN」（401 fail-closed）： 去 Worker 的 Deployments → Version History 看時間軸——如果「Add secret」 是在某次自動部署之前做的，很可能是那次部署把 Secret 整個清掉了 （下一節「keep_vars」有完整說明）。確認方式：Settings → Variables and secrets 現在是不是真的空的；是的話代表要重新設定一次，不是密碼設錯。
  4. 新工具沒出現：連接器快取了舊的工具清單，去 claude.ai Settings → Connectors 把 MyWiki 關掉再開。

keep_vars：自動部署會把 Secret 整個清掉（已修好，但要知道這件事）

Cloudflare 的 wrangler deploy 預設行為是「用設定檔整個覆蓋 Worker」——如果 wrangler.jsonc 裡沒有 "keep_vars": true，Dashboard 上手動設定的 Secret／變數會在每一次自動部署時被清空。2026-08-05 就是這樣：手動設好 MCP_PIN／FIELD_PIN 沒多久，合併 PR 觸發的自動部署就把兩個 Secret 都沖掉了，MyWiki 連接器因此連不上，而且從連接器那端完全看不出「是伺服器的 Secret 不見了」， 只會看到含糊的連線失敗。fieldlog／mcp／cloudflare 三個 Worker 的 wrangler.jsonc 現在都已經補上 keep_vars: true， 並且有 tests/wrangler-keep-vars.test.js 這支測試把關，之後改設定檔不小心漏掉 這一行的話，npm test 會直接報錯提醒，不會再無聲無息重演一次。

9. 維運速查

改完程式碼怎麼上線

三個 Worker 都接 GitHub 自動部署——push 到分支就會自動重新部署， 不用手動觸發。到 Cloudflare Dashboard 對應 Worker 的 Deployments 看狀態。

不要用 Dashboard 的「Edit code」直接改線上程式碼。 那會產生一個「Manually deployed」版本蓋掉 git 部署，之後 git 推上去的東西可能不會生效， 而且很難察覺。

Build 設定：Deploy command 跟「非正式分支」的那組是分開的

Cloudflare Dashboard 的 Settings → Build 裡有兩組長得很像的欄位：

  • Deploy command：只有 push 到 Production branch （Branch control 那裡設定的那條，例如 codex/kiwi-integration）才會用到
  • Non-production branch deploy command（介面上有時顯示成 Version command）：push 到其他任何分支都是走這一組

兩組都要帶正確的 --config .../wrangler.jsonc，只改對其中一組的話， 另一組對應的那些分支每次 push 都會 build 失敗——2026-08-05 就在這裡卡了一輪， 症狀是「隨便一個不相干的 commit 推上去也 build failed」，因為問題出在設定本身， 跟推了什麼內容無關。
